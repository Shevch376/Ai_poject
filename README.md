# XolidayAI — мобильный frontend

Мобильное приложение для подбора досуга: пользователь проходит онбординг, авторизуется, общается с AI-ассистентом и получает рекомендации в виде карточек мест и фильмов. В приложении также есть избранное, профиль, экран подписки, календарь и дополнительные разделы продукта.

Проект командный. В этом репозитории находится портфолио-версия мобильного frontend на Python/Kivy/KivyMD. Backend, приватные ключи, пользовательские данные, сборочные директории и APK-файлы в репозиторий не включены.

**Стек frontend:** Python, Kivy, KivyMD, Requests, websocket-client, Pyjnius, Buildozer, Android.

## Моя роль

Моя зона ответственности — мобильное приложение и его интеграция с backend.

Backend разрабатывался другим разработчиком. Я не писал серверную часть, AI-модель, рекомендательные сервисы и серверную логику подписок. Моя работа была на стороне клиента: интерфейс, пользовательские сценарии, API-клиент, WebSocket-чат, обработка реальных ответов backend и подготовка приложения к Android-сборке.

## Интеграция с backend

В `main.py` реализован API-клиент поверх `requests`. Базовый адрес backend берется из `api_config.json` или из переменной окружения `XOLIDAY_API_BASE_URL`.

Используемые сценарии API:

- `POST /api/v1/auth/register` — регистрация пользователя;
- `POST /api/v1/auth/login/mobile` — вход по email;
- `POST /api/v1/auth/google/login/mobile` — вход через Google mobile flow;
- `POST /api/v1/auth/refresh/mobile` — обновление токена;
- `DELETE /api/v1/auth/logout` — выход из аккаунта;
- `GET /api/v1/me` — загрузка профиля;
- `PATCH /api/v1/me` — сохранение профиля;
- `GET /api/v1/chats` — список чатов;
- `POST /api/v1/chats` — создание чата;
- `GET /api/v1/chats/{chat_id}/messages` — история сообщений;
- `POST /api/v1/chats/{chat_id}/messages` — отправка сообщения;
- `DELETE /api/v1/chats/{chat_id}` — удаление чата;
- `POST /api/v1/messages/{message_id}/reactions` — установка реакции;
- `DELETE /api/v1/messages/{message_id}/reactions` — удаление реакции;
- `DELETE /api/v1/messages/{message_id}/stop` — остановка генерации;
- `GET /api/v1/favorites/cards` — список избранных карточек;
- `POST /api/v1/favorites/cards/{base_card_id}` — добавление карточки в избранное;
- `DELETE /api/v1/favorites/cards/{base_card_id}` — удаление карточки из избранного;
- `GET /api/v1/services/films/genres` — жанры фильмов;
- `GET /api/v1/services/films/discover` — поиск фильмов.

Для чата также используется WebSocket:

```text
/ws/?token=<access_token>
```

На клиенте обрабатываются:

- входящие сообщения;
- статусы генерации;
- обновление истории;
- реакции;
- favorite-состояние карточек;
- принадлежность сообщения пользователю или ассистенту;
- карточки мест и фильмов;
- время сообщений.

## Работа с AI-ответами и карточками

Frontend не реализует AI-модель. Он получает ответ от backend и отвечает за то, как этот ответ выглядит в мобильном приложении.

На клиенте сделано:

- разделение сообщений пользователя и ассистента;
- отображение времени сообщений;
- форматирование текста AI-ответа;
- очистка неподдерживаемых символов, которые некорректно отображались в Kivy;
- вывод карточек рекомендаций внутри ответа;
- обработка карточек мест и фильмов;
- переход из карточки в деталку;
- сохранение карточки в избранное;
- удаление карточки из избранного.

## Оптимизация чата

Чат оказался самым тяжелым экраном приложения: в истории могут быть длинные ответы, форматированный текст и несколько карточек рекомендаций.

Что было сделано для оптимизации:

- история хранится как данные, но в UI одновременно отрисовывается только ограниченное окно сообщений;
- для карточек в чате используется облегченный canvas-рендер вместо большого набора вложенных KivyMD-виджетов;
- изображения в компактных карточках чата не подгружаются, чтобы не тормозить прокрутку;
- лишние вызовы автоскролла объединены;
- рендер карточек адаптирован под длинную историю сообщений;
- лимит истории берется из локальной OpenAPI-выгрузки, если она доступна.

Карточки внутри видимого ответа показываются сразу. Механики раскрытия `show more` в чате нет.

## Android

Проект подготовлен к сборке APK через Buildozer.

В `buildozer.spec` настроены:

- основной файл приложения: `main.py`;
- включение файлов `py`, `kv`, `png`, `jpg`, `ttf`, `ico`, `json`;
- зависимости `python3`, `kivy`, `kivymd`, `requests`, `websocket-client`, `pyjnius`;
- permissions `INTERNET` и `RECORD_AUDIO`;
- режим клавиатуры `adjustResize`;
- AndroidX;
- Google Sign-In dependency;
- сборка под `arm64-v8a` и `armeabi-v7a`;
- портретная ориентация.

Для production-сборки backend должен быть доступен по стабильному HTTPS-адресу. В портфолио-версии реальный адрес сервера не публикуется.

## Структура проекта

```text
.
  main.py                 # логика приложения, screens, API-клиент и чат
  *.kv                    # Kivy/KivyMD-разметка экранов
  assets/                 # локальные изображения и графика
  buildozer.spec          # конфигурация Android-сборки
  api_config.json         # пример настройки backend URL
  cities.txt              # локальный список городов
```

## Настройка backend URL

В портфолио-версии указан placeholder:

```json
{
  "api_base_url": "http://your-backend-host:8000"
}
```

Для локальной разработки можно изменить `api_config.json` или задать переменную окружения:

```bash
XOLIDAY_API_BASE_URL=http://localhost:8000
```

## Локальный запуск

После установки зависимостей приложение запускается командой:

```bash
python main.py
```

Для работы авторизации, профиля, чата, избранного и рекомендаций нужен доступный backend.

## Android-сборка

Типовая debug-сборка:

```bash
buildozer android debug
```

Собранные APK/AAB-файлы не хранятся в репозитории.
